## 结论

1. **新建连接与中大数据包：Go / Rust 约为 Python 的两倍速**
   首包 320 µs → 194 / 190 µs，1 KiB 稳态 96 µs → 56–60 µs，两级转发首包 639 µs → 263–293 µs。
   这对短连接、切换上游、TLS 握手等场景收益最直接。
2. **吞吐：Rust > Go > Python**
   单流 Rust 51–54 Gbps、Go 44–45、Python 27–29；四流 Rust 56–57、Go 46–49、Python 36–39。
   按每核效率看 Rust 也最高（37–42 Gbps/核），Go 的四流每核效率反而低于 Python
   （27 Gbps/核），说明 Go 的绝对吞吐优势主要来自多吃核。
3. **1 字节稳态：Python 最好**
   Python 3.2 µs，Rust 3.7 µs，Go 5.1 µs。极小包下 goroutine/task 唤醒与跨核调度成本
   盖过了语言本身的解析开销；一旦 payload 到 KiB 级结论就反转。
4. **高并发 HTTP：Python 在 8 / 64 并发下占优**
   单线程事件循环的缓存局部性更好；tokio 每连接一个 task、Go 每连接一个 goroutine，
   8 连接会分散到多个核。并发 64 时三者都撞上客户端（Python 生成器）瓶颈，
   p50 齐齐进入毫秒级，差距缩小。
5. **故障切换：Go / Rust 更好**
   拒绝连接时约快 40%（511 → 297/302 µs）；黑洞场景三者都精确落在 1 s 超时上；
   全部不可用时 Rust 多花约 300 µs 做有序 `shutdown`，换来客户端拿到干净 EOF 而不是 RST。
6. **负载下的效率：Rust 最省 CPU**
   2 条背景流时 Rust 63.4 Gbps / 74%，Go 52.2 Gbps / 81%，Python 31.9 Gbps / 90%。

## 局限

- 每份实现只跑了一轮完整 `all`；并发 8/64 与吞吐多流接近饱和点，方差较大，
  建议在决策前再各跑 2–3 轮取中位数。
- 三份实现在同一台机器上共用 loopback，客户端（Python 生成器 / ab / iperf3）本身
  在并发 64 与多流吞吐时也是瓶颈，绝对值偏保守。
- Go 版版本号为 0.2.0，Python / Rust 为 0.1.5；版本号差异见各自的 `version` 命令实现，
  不影响本轮的转发与 CLI 对齐性。

## 复现

```bash
python bench/bench.py all --impl python --offset 100
python bench/bench.py all --impl go     --offset 100
python bench/bench.py all --impl rust   --offset 100
```

三份实现必须**串行**执行，否则 iperf3 / 客户端会互相抢 CPU，尾延迟与吞吐都会被污染。
